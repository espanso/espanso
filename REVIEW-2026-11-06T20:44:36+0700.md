# Production-ready bar for this PR

- Detector-init failure no longer panics the engine thread (the PR claim): the `init_and_spawn` error is logged and the engine thread returns `ExitMode::Exit`.
- End-to-end chain breaks the systemd restart loop: worker exits `WORKER_SUCCESS` (0) → daemon `_` arm returns 0 → launcher `Ok` → `Restart=on-failure` sees success → no restart.
- `ui_remote.exit()` in the new arm is safe on every platform: it is the identical call the normal shutdown path makes (`engine/mod.rs:321`), and on Linux it is an unbounded-channel send that cannot fail while the UI loop owns the receiver.
- Both log hints are accurate (`USE_EVDEV` is read at `worker/mod.rs:91`; `wayland` is a real build feature).
- No scope creep: 1 file, failure branch only; the success path and every other `expect` in the startup sequence are untouched.
- No secrets, machine paths, or license-header changes; `cargo fmt --check`, `cargo check`, and `cargo test -p espanso --bin espanso` are green.

Exit code on detector-init failure changes 101 (panic, restart loop, `start-limit-hit`) → 0 (clean stop, journal carries cause + hints, systemd does not restart). ## 8. Adversarial review

Tried to falsify readiness and failed on every axis:
- Most-likely-wrong assumption: "`ui_remote.exit()` is unsafe this early (UI loop not running yet)." Falsified: on Linux it is `unbounded().send()`, which buffers until the loop starts and fails only if the receiver is dropped — the receiver is owned by `worker_main`'s eventloop, which outlives the joined engine thread. Same call, same safety as the normal path.
- Happy-path-only logic: none; the diff touches only the failure branch, and the success destructuring is preserved verbatim in the `Ok` arm.
- What breaks first in production: a host with neither XRecord nor evdev permissions gets a stopped espanso with two hint lines — recoverable by following the hints, versus the old unrecoverable restart loop. Strictly better on every axis.
- False-confidence test: `cargo check --all-features` compiles the changed `match` on all feature combos; a tuple-shape drift in `init_and_spawn` would fail here, not in production.
- Contract drift: no signature changed (`initialize_and_spawn` still returns its handle `Result`), so no caller contract moved.
